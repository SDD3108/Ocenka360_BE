# Email, сессии и согласия

## Локальная отправка и SMTP

По умолчанию local использует console backend: письмо видно в runserver. SMTP не обязателен для разработки, а реальные письма требуют работающего почтового сервиса. Адрес поддержки `sati-ocenka@mail.ru` сам по себе не даёт права отправлять от него письма.

Для реальной отправки в локальной `.env`:

```dotenv
EMAIL_DELIVERY_MODE=smtp
EMAIL_HOST=SMTP_HOST_FROM_YOUR_PROVIDER
EMAIL_PORT=587
EMAIL_HOST_USER=YOUR_SMTP_LOGIN
EMAIL_HOST_PASSWORD=YOUR_APP_PASSWORD
EMAIL_USE_TLS=True
EMAIL_USE_SSL=False
DEFAULT_FROM_EMAIL=Ocenka 360 <YOUR_VERIFIED_SENDER>
```

Параметры возьми в аккаунте почтового провайдера, не копируй placeholders как готовые значения. Для порта 465 обычно SSL=True и TLS=False, но следуй параметрам провайдера. Не включай оба. Перезапусти сервер. Используй пароль приложения/SMTP credential, не публикуй его в Git или чате. Production всегда использует SMTP независимо от EMAIL_DELIVERY_MODE. Платность и квоты определяет провайдер; бесплатная неограниченная доставка не обещана. SMTP acceptance не гарантирует попадание во входящие — проверь spam и настройки отправителя.

Ошибка соединения/отправки возвращает 503, код не становится пригодным к входу. Предыдущий успешно отправленный код остаётся действительным до своего срока, если следующая отправка не удалась. Только успешная новая отправка инвалидирует более старые коды.

## Лимиты

Код: 6 цифр, 10 минут, максимум 5 проверок на challenge. Повторная отправка не раньше 60 секунд. На час: 5 запросов на email, 30 на IP; проверок кода 60 за 10 минут на IP. Общий дневной cap 500 запросов регулирует OTP_GLOBAL_DAILY_LIMIT. Окна фиксированные; попытки, остановленные последующим лимитом или ошибкой SMTP, могут уже расходовать предыдущие квоты. Это консервативное ограничение расходов, а не счётчик доставленных писем.

Лимиты хранятся в общей БД и не исчезают при перезапуске workers. IP берётся из REMOTE_ADDR, входящий X-Forwarded-For не доверяется. За reverse proxy до запуска необходимо настроить доверенное восстановление IP на уровне сервера/инфраструктуры и закрыть прямой порт; иначе все пользователи будут делить лимит IP прокси. Защита от объёмного DDoS требует внешнего уровня.

## JWT для Expo/Next.js

Access живёт 10 минут, сессия — максимум 30 дней с первого входа. Refresh rotation не продлевает абсолютный срок. JWT подписан; payload не зашифрован, персональные документы туда не помещаются. Каждая авторизация проверяет активного пользователя, session id, отзыв и token_version в БД.

Клиент должен выполнять **один refresh за раз** (общий Promise/mutex для параллельных Axios запросов), сохранять новую пару перед повтором ожидающих запросов и повторять исходный запрос максимум один раз. Повторное использование старого refresh считается replay и отзывает сессию, включая уже выданный access. Если ответ refresh потерялся после обработки сервером, повтор старого токена приведёт к новому входу; сервер не возвращает прежнюю пару повторно.

Expo: refresh хранить в SecureStore, не AsyncStorage, URL или логах. Для Next.js при реализации кабинета выбрать серверный BFF с HttpOnly cookie и CSRF-защитой; этот Part выдаёт JSON-токены и сам cookie-BFF не реализует. Не складывать refresh в localStorage. Успешный logout API — 204; удалить локальные токены. Если сервер недоступен, локальное удаление не означает подтверждённый отзыв на сервере.

Смена DJANGO_SECRET_KEY отзывает все JWT и делает старые OTP непригодными; ключ не менять при обычном обновлении Part. Отключённый пользователь не может использовать активные токены. Logout-all отзывает JWT-устройства; Django Admin cookie — отдельная сессия.

## Документы и 18+

Три вида: terms, privacy, personal_data. Идентификатор, версия, язык, полный текст и SHA-256 возвращаются API; принятие привязано к конкретной неизменяемой версии. Черновики `dev-1` нужны только для локальной проверки интерфейса. Не использовать их как соглашения с реальными клиентами.

При регистрации сначала подтверждается email и создаётся минимальный аккаунт, затем принимаются документы; требуется явно показывать этот порядок в UI. Предварительное ознакомление доступно публично через /legal/documents/. Подтверждение взрослого возраста — декларация, не KYC. Политика для реальных данных регистрации должна быть утверждена до публичного запуска.

Для production нужно заполнить COMPANY_LEGAL_NAME и через admin создать утверждённые документы всех трёх видов для ru/kk/en, с новой версией, `is_draft=False`, `is_active=True`. Действующий документ каждого вида/языка может быть только один. Для обновления сначала отключить предыдущую версию, затем активировать новую; в промежутке API сознательно отвечает legal_not_ready. Создание/публикация — только суперпользователь. Существующий текст не редактируется: исправление — новая версия. История согласий не редактируется в admin.

До согласия разрешены вход, профиль, документы и управление сессией. Для будущих операций с заявками предусмотрен `HasAcceptedCurrentDocuments` (сочетать с аутентификацией и проверкой владельца). Заявок в Part 2 ещё нет. Согласие на Gemini, платёжные условия, сроки обязательного хранения и удаление аккаунта будут реализованы отдельно; текущее согласие не даёт автоматически разрешения на любые будущие функции.

## Обслуживание

Планировать раз в сутки на сервере (scheduler в этом архиве не установлен):

```bash
python manage.py cleanup_auth --settings=config.settings.production
```

Удаляет квоты с истёкшим сроком, старые cooldown, OTP спустя сутки после expiry и сессии спустя 30 дней после expiry. Пользователи и согласия не удаляются. Сроки относятся к техническим данным авторизации, не к клиентским отчётам и документам. Системная почтовая очередь ещё не реализована: запрос SMTP синхронный с таймаутом.
