# Границы безопасности Part 1

## Реализовано

- Закрытый по умолчанию REST API; публичные endpoints перечислены явно.
- UUID вместо последовательных ID пользователей; UUID сам по себе не заменяет права доступа.
- Защита структуры ролей ограничениями БД и проверками Django Admin.
- Только суперпользователь управляет учётными записями в технической панели.
- Администратор не может удалять пользователей через эту панель; отключает их через is_active.
- Сессионная авторизация Django, CSRF для admin, безопасные настройки cookies/HTTPS в production.
- /me не показывает hash пароля, группы и флаги технического доступа.
- Загруженные документы не обслуживаются публичным URL; загрузка пока не реализована.
- Production отказывается запускаться с SQLite, слабым секретом, wildcard/localhost host либо HTTP origins.
- Все API-ответы помечены no-store; request ID генерируется сервером.
- Непредвиденные ошибки API дают обобщённый ответ без внутреннего exception text.
- `.env`, базы, загруженные файлы и виртуальное окружение исключены из Git и релизного ZIP.

## Ограничения и дальнейшая работа

Не считать Part 1 достаточным для хранения реальных удостоверений, приёма денег или открытой production-регистрации. Пока нет OTP/JWT, удаления аккаунта, юридических согласий, документных разрешений, финального аудита, секрет-хранилища, резервного копирования и мониторинга.

Лимиты DRF используют per-process local-memory cache и не защищают от распределённой атаки. Админский парольный вход пока не имеет account lockout/2FA и должен оставаться локальным или закрытым инфраструктурой (VPN/IP allowlist) до соответствующей защиты. В production потребуются общий limiter/cache, ограничения на reverse proxy и специальная защита OTP с контролем расходов.

Логи Django и reverse proxy в дальнейшем нужно настроить на редактирование чувствительных полей и ограниченное хранение. Не передавать email, ИИН, OTP, токены и имена документов в query-string. Не включать DEBUG с реальными данными.

Публичные репозитории подходят для кода, но не для секретов, удостоверений и клиентских отчётов. Сканы сертификатов для публикации должны проходить отдельную проверку на ненужные персональные данные. Реальные сертификаты и вложения из обсуждения не включены в этот архив.

## Подготовка юридических документов

В последующих Parts понадобятся пользовательское соглашение, политика конфиденциальности, отдельные согласия, условия оплаты/отмены и политика хранения. Пока неизвестно точное юридическое название ИП; его нельзя подменять названием бренда. Пустое COMPANY_LEGAL_NAME означает «не подтверждено».

База и документное хранилище планируются в Казахстане. Передача данных Gemini рассматривается отдельно: минимизация, разрешённые основания, необходимые согласия и платный API через backend. Окончательную оценку и отчёт утверждает специалист. Обязательные сроки хранения согласуются до реализации удаления; произвольные сроки в Part 1 не устанавливаются.

Юридические тексты в этом Part не опубликованы и не считаются принятыми пользователями. `email_verified_at` не равен согласию с документами или подтверждению возраста.
