# Каталог и анкеты — Part 3

## Модель и API

Category хранит стабильный slug, переводы заголовка, порядок и активность. Service хранит категорию, стабильный slug, переводы заголовка/описания, активность и ссылку на текущую опубликованную FormRevision. В версии лежат вопросы, условия и требования к документам; SHA-256 относится ко всему JSON с тремя языками. Опубликованную версию нельзя редактировать через model.save или admin; прямой SQL/QuerySet.update не является поддерживаемым способом изменения каталога.

| Метод и путь от /api/v1/catalog/ | Доступ | Ответ |
|---|---|---|
| GET categories/?language=ru | Публичный | Массив активных категорий с количеством видимых услуг |
| GET services/?language=ru&category=real-estate&q=квартир&page=1 | Публичный | count, next, previous, results; 20 услуг на странице |
| GET services/apartment/?language=ru | Публичный | Карточка услуги, form_id, form_version |
| GET services/apartment/form/?language=ru | Публичный | id, version, checksum, service, language, fields, documents, notice |
| POST services/apartment/validate/ | Вход, подтверждённый email, актуальные согласия, декларация 18+ | Проверка ответов без сохранения |

Язык ru по умолчанию; поддерживаются ru/kk/en, не kz. Фильтр category — slug, q — до 100 символов, поиск по названию на выбранном языке и slug. На SQLite регистронезависимость кириллицы зависит от SQLite collation: надёжнее вводить фрагмент в том же регистре. В production поиск использует поведение PostgreSQL/его locale. Это поиск по подстроке, без морфологии. Неверный язык/страница/неизвестный параметр — 400; отсутствующая страница — 404.

Категория без опубликованных услуг может вернуться с service_count=0. Отключённые услуги/категории и услуги без опубликованной формы исключены из списка и дают 404 на detail/form/validate. JWT не требуется для чтения и просроченный Bearer не блокирует публичный каталог. Записи опубликованных старых версий сохраняются внутри БД, отдельного публичного endpoint чтения истории пока нет.

## Пример проверки квартиры

Сначала запросить актуальную форму; подставить её `id`. Передать `Authorization: Bearer ACCESS_TOKEN` из Part 2 и JSON:

```json
{
  "form_id": "UUID_ИЗ_ОТВЕТА_FORM",
  "language": "ru",
  "answers": {
    "applicant_type": "individual",
    "applicant_role": "owner",
    "purpose": "sale",
    "city": "Астана",
    "address": "Тестовый адрес",
    "area_sqm": "65.5",
    "inspection_preference": "onsite",
    "urgency": "regular"
  }
}
```

200 содержит `valid`, `errors` (ключ вопроса → код ошибки), `visible_fields`, подходящие `documents`, `notice`, `form_id`, `form_version`, `submission_created: false`. Ошибки ответов возвращаются с 200/valid=false; неправильная структура запроса — 400. Пример ошибки: `{"area_sqm":"invalid_decimal","city":"required"}`. Возможные коды: required, invalid_type, invalid_choice, invalid_decimal, invalid_date, out_of_range, too_long, unknown_field, field_not_applicable. Переводить коды в интерфейсе через i18n.

Ответы не записываются в БД, не возвращаются в response и не добавляются в application-логи. Это не черновик заявки. Backend не отправляет WhatsApp/push и не принимает оплату. `valid=true` говорит только о корректности полей, не о достаточности или подлинности документов. Требования к документам — подсказки для следующего этапа, не проверка загруженных файлов.

При смене формы сервис возвращает **409 stale_form**, включая чужой form_id. Нужно получить новую форму, сравнить вопросы и предложить пользователю проверить ответы. Нельзя молча подменить id и повторить отправку. При появлении новой юридической версии проверка даст 403 до принятия актуальных документов.

## Формат definition

Корневой объект: `fields`, `documents`, `notice`. Полный рабочий пример — scripts/catalog_form_example.json. Все подписи, help, notice — объект с ровно тремя непустыми строками ru/kk/en. Тексты plain text, не HTML. Клиент не должен исполнять или вставлять их как HTML.

Поле: `key` (латинская строчная буква, затем до 49 латинских букв/цифр/_), `type`, `label`, `required`. Необязательные `help`, `max_length`, `min`, `max`, `options`, `visible_if` применяются по типу. Неизвестные свойства/типы, повтор ключей, неподдерживаемые условия и отсутствующие переводы не сохраняются.

| Тип | Значение answers | Ограничения |
|---|---|---|
| text, textarea | Строка | trim; по умолчанию до 1000, явный max_length до 4000 |
| choice | Строка стабильного option.value | Только из options, от 1 до 30 вариантов |
| integer | JSON integer | true/false и строка «3» не считаются числом; min/max целые |
| decimal | Строка, например «65.5» | До 12 цифр слева и 4 справа, точка, без экспоненты/NaN; min/max целые либо точные decimal-строки |
| date | Строка YYYY-MM-DD | Реальная календарная дата; будущие даты отдельно не запрещены |
| boolean | JSON true/false | Строки «true»/«false» не подходят; false считается заполненным |

Незаполненные необязательные поля пропускаются. Поддерживается до 50 вопросов, 30 документов, definition до 100000 символов JSON. В answers до 50 ключей; вложенные объекты и списки не поддерживаются. Базовый размер request body ограничен настройками Django; на reverse proxy также нужен лимит.

Обязательный системный вопрос `applicant_type` должен быть без условия, type=choice, required=true, варианты individual и company. Остальные вопросы настраиваются. Не помещать ИИН и загрузку файлов в текущую анкету без отдельного этапа обработки этих данных.

Условие показа поля:

```json
{"visible_if":{"field":"applicant_type","equals":"company"}}
```

Условие может ссылаться только на **предыдущий** choice/boolean вопрос. Это предотвращает циклы и не позволяет выполнять код. Если родитель отсутствует, скрыт или невалиден, дочерний вопрос не показывается. При смене родителя UI должен убрать ответы скрытых вопросов: присланные скрытые ответы отвергаются с field_not_applicable. Неизвестные ответы тоже отвергаются.

Документ содержит `key`, `title`, `help`, `required`, опциональное `when` такого же вида. Условие может ссылаться на любой определённый choice/boolean вопрос, но учитывается только валидный и видимый ответ. При неполной анкете условный список тоже неполный: не выдавать его за окончательный до исправления ошибок. required означает предварительную обязательность подготовки, а не подтверждение наличия файла.

## Работа через admin

Техническая админка доступна прежнему суперпользователю. Роль appraiser не даёт staff или superuser; рабочий кабинет мамы появится отдельно. Каталог в Django Admin редактирует только суперпользователь; даже staff с назначенными model permissions не получает доступ.

1. В «Категории» меняй title, sort_order, is_active. Для каждой подписи нужны три перевода.
2. В «Услуги» меняй title, summary, категорию и активность. Slug существующих записей не меняется. current_form readonly и переключается публикацией.
3. В «Версии анкет» выбери **одну** версию и действие «Создать редактируемую копию». Создастся следующий номер для этой услуги, с копией вопросов и требований.
4. Открой новый черновик, отредактируй definition, сохрани. До публикации клиенты видят предыдущую версию.
5. В списке выбери черновик и «Опубликовать и сделать текущей». Публикация и переключение текущей версии выполняются в одной транзакции. Действия clone/publish записываются в Django Admin LogEntry.
6. Опубликованные записи доступны только для просмотра. При исправлении создай новую копию. Можно повторно назначить старую опубликованную версию текущей через то же действие; клиенты со сменившимся form_id получат 409.

Для новой услуги создай Service, затем FormRevision с version=1 и подходящим JSON. До публикации она не попадёт в публичный API. Не удаляй версии: в следующих Parts заявки будут ссылаться на сохранённую версию. Удаление через admin запрещено; используй is_active=False для скрытия.

`seed_catalog` предназначен для первого заполнения: существующий slug не перезаписывается. Даже выключенные услуги и изменённые формы сохраняются. Не используй seed как сброс каталога; никаких --reset/--force с удалением нет. Все начальные формы сразу опубликованы для разработки; до публичной эксплуатации оценщик должен проверить списки и переводы.

## Границы и продолжение

Схема API подготовлена для Expo и Next.js. UI-конструктор форм в этом Part не создаётся; редактирование definition идёт через JSON в Django Admin. Полезно хранить утверждённые JSON в приватном процессе разработки, но не реальные ответы клиентов в публичном Git.

Никаких тарифов, гарантированных сроков, автоматического утверждения удалённого осмотра или официального расчёта ДТП в Part 3 нет. Список направлений опирается на https://ocenka360.kz/ и требования владельца; условия документов — предварительная конфигурация, не исчерпывающая юридическая норма. Неутверждённые коммерческие правила не подставлены автоматически.

Part 4 должен повторно проверять опубликованную версию, права пользователя и согласия **в момент сохранения заявки**, применять evaluate на сервере и сохранять ссылку на неизменяемую FormRevision. Предыдущий успешный validate не является разрешением на запись и не устраняет гонку между предварительной проверкой и изменением каталога. Part 5 добавит файлы с проверкой владельца, типов и приватного доступа.
