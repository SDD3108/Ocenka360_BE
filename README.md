# Оценка 360 — Backend, Part 1

Рабочая основа Django API для приложения «Оценка 360». Версия **0.1.0**.

В этом Part реализованы пользовательская модель с email вместо username, роли, техническая административная панель, базовые API, миграции, OpenAPI и проверки доступа. Клиентский вход по email-коду появится в **Part 2**. Этот архив не является готовым к запуску бизнеса приложением.

## Что уже работает

- Роли `client`, `appraiser`, `admin`; UUID пользователей.
- Email без учёта регистра, уникальность на уровне БД, безопасное хеширование паролей администратора.
- Создание администратора через `createsuperuser`; управление пользователями через `/admin/`.
- Пользователи не получают права администратора по данным, присланным клиентом.
- Проверки доступности процесса и базы; публичная конфигурация для Mobile Part 1.
- Чтение собственного профиля через серверную сессию администратора.
- Настройки local / test / production, CORS по списку, JSON-ошибки, идентификатор запроса.
- OpenAPI YAML и локальный Swagger UI без внешнего CDN.
- Автотесты и конфигурация GitHub Actions для SQLite/PostgreSQL.

## Запуск на Mac с нуля

Нужен **Python 3.12**. JavaScript/JSX будут в мобильном приложении и веб-кабинете; backend по согласованному стеку написан на Python.

1. Распакуй ZIP. Открой папку `Ocenka360_BE` в VS Code.
2. Если уже клонировал свой репозиторий, перенеси **содержимое** папки из ZIP в корень клона, рядом с его `.git`. Не создавай вложенную `Ocenka360_BE/Ocenka360_BE`. Перенеси также `.gitignore`, `.env.example`, `.env.production.example`, `.github`.
3. В терминале этой папки выполни:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements/dev.txt
python scripts/init_env.py
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

Если `python3.12` не найден, установи Python 3.12 с официального python.org, затем открой терминал заново. Если Python 3.12 уже доступен под именем `python3`, используй `python3 -m venv .venv`.

`init_env.py` создаёт `.env` с уникальным локальным секретом и не перезаписывает существующий файл. SQLite создаётся автоматически; Docker и отдельный сервер базы для первого запуска не нужны.

В `createsuperuser` укажи свою почту и новый пароль длиной от 12 символов. Пароль в терминале не отображается — это нормально. Готовых логинов/паролей в архиве нет. Подтверждение владения email пока не выполняется: это технический администратор, а не регистрация клиента.

Открой:

| Адрес | Назначение |
|---|---|
| http://127.0.0.1:8000/admin/ | Вход администратора по email и паролю |
| http://127.0.0.1:8000/api/v1/ | Название API и версия |
| http://127.0.0.1:8000/api/v1/health/live/ | `{"status":"ok"}` — процесс отвечает |
| http://127.0.0.1:8000/api/v1/health/ready/ | Доступность соединения с БД |
| http://127.0.0.1:8000/api/v1/config/ | Контакты, языки, доступные возможности |
| http://127.0.0.1:8000/api/docs/ | Документация Swagger |
| http://127.0.0.1:8000/api/v1/accounts/me/ | Собственный профиль после входа в `/admin/` в том же браузере |

Для сессии используй один и тот же адрес: `localhost` и `127.0.0.1` имеют разные cookies.
Корень `/` пока намеренно не содержит сайта и возвращает 404.

## Создание учётной записи мамы

После входа суперпользователем: **Пользователи → Добавить**. Укажи email, имя, роль **Оценщик**, язык, телефон и временный сильный пароль. Оставь «Активный» включённым. Не включай `is_staff`/«Статус персонала» и `is_superuser`/«Статус суперпользователя».

Это создаёт запись для следующих Parts. У оценщика пока нет собственного рабочего кабинета и клиентского входа; они появятся позже. Пароль в этой форме не меняет согласованную модель входа клиентов по email-коду. Будущие OTP-клиенты смогут иметь непригодный для парольного входа пароль.

Техническая админка Django отличается от будущего удобного кабинета на Next.js. Назначение ролей и флага staff — разные операции; роль оценщика никогда не даёт доступа к Django Admin.

## Повторный запуск

```bash
source .venv/bin/activate
python manage.py runserver 127.0.0.1:8000
```

Остановить сервер: `Control + C`. Сбросить забытый пароль администратора:

```bash
python manage.py changepassword your-email@example.com
```

## Проверка

```bash
python -m pip check
ruff check .
ruff format --check .
python manage.py check --settings=config.settings.test
python manage.py makemigrations --check --dry-run --settings=config.settings.test
python manage.py test --settings=config.settings.test
python manage.py spectacular --settings=config.settings.test --file docs/openapi.yaml --validate --fail-on-warn
```

Тесты используют отдельную временную SQLite, а не локальную рабочую БД. Для PostgreSQL есть `TEST_DATABASE_URL` и CI; описание в `docs/DEVELOPMENT.md`. Результаты проверки этого архива — в `docs/VALIDATION.md`.

## Что ещё не реализовано

Email-коды и JWT, регистрация и редактирование профиля, согласия/удаление аккаунта, каталог, заявки, загрузка документов, платежи, возвраты, промокоды, календарь, push, Gemini, расчёты и кабинеты. В `/api/v1/config/` соответствующие возможности честно выключены. За авансом 2 000 ₸ пока не стоит платёжный endpoint.

Публичного `/register/`, выдачи токенов, тестового универсального кода или обхода авторизации нет. `/accounts/me/` без сессии возвращает **403** — это ожидаемое поведение текущего SessionAuthentication. Мобильная авторизация и её контракт добавятся в Part 2.
